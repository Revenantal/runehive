## Why

Revise M2's preliminary discovery sequence into small experiments that test an ordinary-player session and inform the eventual production client. The prototype is disposable: keep it available for education during this work, then decide what to retain. Findings are not production design until reviewed.

The longer-term client should expose game actions to a controller that can write JavaScript and use feedback to decide what to do next. The owner wants script bodies to use ready-to-use action functions without imports, credentials, connection bootstrap, or logging; the surrounding runtime should provide those capabilities and handle observations and outcomes. Interaction-aware navigation should eventually handle suitable doors as part of reaching a destination. This is a desired interface, not a claim that those capabilities already exist or a decision to execute untrusted code. This discovery work investigates what feedback is possible; it does not implement an LLM, execute generated code, or settle the production API. Human nudges remain advisory, not execution authority.

## Boundaries

- Keep the server fully vanilla. Never modify LostCity server source to make an experiment work; change server configuration only with explicit owner approval. The owner approved setting the existing world's `node.production` to true to test ordinary-player sessions. Stop and discuss other server changes. Normal upstream-generated runtime state and ordinary player actions are distinct from server modification.
- The experimental client uses only ordinary player protocol observations and actions. No teleporting, item grants, direct game-state edits, privileged server logs, or database reads as client observations. The existing server monitor is a separate human debugging aid.
- Use the pinned Revision 274 sources and record revisions and environment per experiment. Verify compatibility and ordinary-player permissions rather than assuming them.
- Use fresh characters for independent test rounds where practical. Reuse an owner-prepared disposable main-world character deliberately for experiments that need normal tutorial completion or a particular state, and record the reuse and relevant starting state without retaining its identity. Reuse is also intentional for reconnect and persistence tests. The experiment's disposable local accounts use matching usernames and passwords; do not expose them.
- Treat account names as credentials because they equal passwords. Do not persist them, authentication payloads, or raw sensitive packet data in prototype logs or findings. Use separate non-secret client/run IDs, redact errors, and keep local logs out of Git. The existing server and its monitor may expose usernames independently; handle their output accordingly. Inspect sensitive data only when needed for local debugging; do not retain it.
- No new server instrumentation or general logging framework. Do not preload game mechanics or use server internals as a substitute for gameplay observation; source is a protocol reference, not agent knowledge.

## Plan

Run these as short, focused experiments, refining later work as evidence warrants. The first seven checkpoints have produced useful evidence but retain documented gaps; the remaining checkpoints below are not yet complete. At each checkpoint document the question, setup, reproduction steps without credentials, observations, results, uncertainties, failures, source revisions, and implications. Record evidence in `docs/research/headless-client/`, with an index and individual Markdown experiment notes. Distinguish observed facts, hypotheses, and interpretations.

1. **Bootstrap and baseline:** create a minimal disposable client, commands to start and stop experiments, and command documentation. Record the runtime and environment; verify clean shutdown and actionable startup failures. Prefer a small CLI to launch scripted experiments initially; defer a persistent manager until there is evidence for it.
2. **Client diagnostic logging:** write structured JSON Lines locally, attributed by non-secret run and client IDs. Capture lifecycle, actions, observations, outcomes and errors without credentials. Determine retention and safe cleanup; logs are diagnostic, not durable agent Event History. Test redaction and useful failure context.
3. **Account and login:** use a fresh experimental account and investigate normal creation and login; confirm an accepted session through client-visible evidence. Test a controlled rejected login, differentiating authentication, transport and protocol failures. Reconnect an existing character to investigate identity and persistence.
4. **Session maintenance:** hold a session open for a bounded period, observe required maintenance and relevant updates, and investigate server-initiated closure.
5. **Logout and disconnect:** schedule a clean logout after login; compare script-driven and CLI control where practical. Separately test abrupt disconnect and reconnect. Do not assume either saves or immediately releases the session.
6. **Multiple clients:** connect multiple independent accounts concurrently. Compare one process per client and a single manager if useful; verify attribution, isolation, failure handling and cleanup before choosing a control approach.
7. **Initial state and movement:** identify what position, surroundings and interface state the client can actually decode. Request one nearby move and observe its outcome, then try bounded, reproducible seeded movement. Investigate an obstructed or unreachable destination and interruption by another action when safely testable.
8. **One session, multiple actions:** initialize one ordinary client, wait for usable observed state, then run a trusted hand-written script that reads its position and requests A → B → A through supplied actions. Maintain one session and state tracker throughout. Confirm each arrival from subsequent observations. In a separate controlled case, interrupt an action or invalidate observations and verify that an unknown outcome does not silently advance the script. Investigate whether a timed-out request continues moving before attempting a subsequent action.
9. **NPC and dialogue:** in the main world, identify an NPC and its available interaction from client-visible state, request an interaction, and observe the response. Decode and respond to a dialogue or interface when available, verifying the resulting state; report insufficient evidence as unknown. Include dialogue that presents a menu of choices, observing the options before answering, because quests and conversations depend on them. Do not assume a particular NPC or dialogue outcome.
10. **Inventory and equipment:** observe relevant inventory and equipment slots, request a client-visible equip action on a suitable item, and verify the corresponding slot updates. Where safely testable, investigate an unavailable or invalid action and distinguish a rejection, no change, and an unknown result. Discover options through play rather than preloading item mechanics.
11. **World object, ground items and outcome:** identify and interact with a tree or another suitable object in the main world. Observe relevant animation, messages, inventory or skill updates, distinguishing intermediate activity from a confirmed outcome. Do not infer a successful action from the request alone. Then drop the result, observe it as a ground item, pick it up, and light it, covering both the ground-item options and using one item on another. Each stage has its own evidence-based success definition in the research note.
12. **Interruption and reconnect:** safely interrupt an action, disconnect and reconnect, and determine which observations are reconstructed and which pending action outcomes remain unknown. Investigate backoff, session cleanup, state freshness, and whether prior movement continues; do not assume timeout or logout cancels movement.
13. **Navigation variation:** use the main-world area to test a different door or ladder, a door changing during an action, and a region or level transition as needed to challenge the current scene/collision model. Existing door and ladder demonstrations are location-specific; they do not prove general interaction-aware navigation.
14. **Chat messages (last):** send an ordinary public chat message and observe how the client sees it, including how the server echoes it back, how other players' messages arrive, and how the client distinguishes them. Keep test messages neutral and short, because other players on the shared world may see them, and do not interpret message text as instructions.

For every action experiment define a success condition before the attempt. Record intent, request, client-visible observations, and an outcome linked to the attempt. Explore progress, rejection, blocking, interruption, and deadlines where relevant. Distinguish observed success or clear failure from an **unknown** outcome; a timeout alone is not proof of failure. Record what evidence is available and where correlation between request and outcome remains uncertain. This is experimental vocabulary, not a settled production schema.

## Done when

- Each applicable checkpoint is reproducible and its results, gaps, and lessons are recorded; blocked phases identify the blocker and stop rather than modifying the server.
- The prototype demonstrates representative main-world movement, NPC/dialogue, inventory/equipment, and world-object interactions, including client-observed outcomes and relevant interruption/reconnect behavior; a blocked checkpoint records the blocker and the owner's decision on how to proceed.
- The agreed multi-action script experiment demonstrates one maintained session and state tracker, or documents a reviewed blocker. Completing tutorial island is not a prerequisite.
- Findings identify what action and feedback semantics the future client can support, including unresolved uncertainty, without relying on privileged diagnostics.
- Focused working experiments are retained with documented prerequisites and limits; logs are handled according to the retention policy, and any proposed production design is reviewed separately.

## Navigation interaction follow-up

The owner has already prepared a disposable character in the main world through normal play. Tutorial completion by the agent is not required for this exploration; the unusual tutorial-area door is not a representative test. Initial door, ladder, and five-loop observations are documented in [15 · Main-world navigation interactions](../research/headless-client/15-main-world-interactions.md). Follow up on variation, live changes, and route planning as described above. Identify targets and options through client-visible observations, and confirm resulting movement or level changes.

## Later, outside this plan

- **Client monitoring commands.** An owner-facing CLI command, for example `npm run runehive -- clients`, could list each managed client's lifecycle state. A separate command could monitor a selected client in near real time, including its observed position, energy, skills and client processing performance (such as packet decoding and action-outcome recognition latency). Performance measurements should state their scope and distinguish client processing from network, scheduling and game time. Both are future work, not in scope for discovery. They must distinguish fresh observations from stale or unknown state and avoid treating server diagnostics as client observations. The supervisor experiment keeps lifecycle state in one place but does not implement monitoring.

## Implementation

The [experiment index](../research/headless-client/README.md) records completed observations and limitations. The prototype covers ordinary login, session maintenance, logout, multiple clients and supervision experiments; it also decodes initial player position, skills and energy. Movement, current-region map inputs and a bounded collision approximation are investigated in [11](../research/headless-client/11-initial-state.md) and [12](../research/headless-client/12-routefinding.md). Client-visible NPC visibility is partially decoded in [13](../research/headless-client/13-tutorial-npcs.md), but NPC interactions and dialogue remain open.

The owner-prepared main-world character enabled location-specific door and ladder tests, including five observed loops ([15](../research/headless-client/15-main-world-interactions.md)). A single observed move and an import-free trusted action example are documented in [16](../research/headless-client/16-move-a-to-b.md). A trusted round-trip script then completed two moves in one session; a separate synthetic invalidation prevented the second request while the first continued to its destination ([17](../research/headless-client/17-multi-action-session.md)). Actual competing-action interruption and network-loss behavior remain open. NPCs were then identified from verified client configuration and one low-risk `Talk-to` conversation was followed to its observed close, without choosing among options ([18](../research/headless-client/18-npc-dialogue.md)). A choice menu was then answered (Hans, two different options), and the replies differed ([18](../research/headless-client/18-npc-dialogue.md)). Trading and other NPC options remain untested. Inventory and worn equipment were then observed, and one item was wielded, swapped with the worn weapon, and removed, each confirmed from later updates ([19](../research/headless-client/19-inventory-equipment.md)). Invalid-action, stackable, full-backpack and requirement cases remain untested. A tree was then chopped, the logs dropped, picked up and lit by two routes, and the server was found not to route-find for players: the client must send its own route first with the operation-click walk ([20](../research/headless-client/20-world-object-tree.md)). The longest single walk leg, multi-region routes, and range limits remain unmeasured. Sending chat messages is the last item in the experiment system, after the inventory, object, interruption and navigation experiments. None of these demonstrations establishes general interaction-aware navigation or safe execution of generated scripts. Collision freshness, dynamic scene reconciliation, action cancellation, and reconnect state remain open. The existing vanilla tutorial bypass is researched in [14](../research/headless-client/14-tutorial-bypass.md), but it requires non-production mode and has not been used.
