# Main-world navigation interactions

[Experiment index](README.md) · [Discovery plan](../../plans/headless-client-discovery.md)

The owner prepared a disposable character in the main world by normal play for door and ladder experiments. It logged in as an ordinary player. Client-observed position and validated current-region client assets identified a nearby location named `Door` with first option `Open`, and a `Ladder` with first option `Climb-up`. Static region assets can be stale; this is not independent proof of the current dynamic scene.

These experiments used the shared owner-hosted server in production mode, not a separate server. ## Door experiment defined before running

From the observed adjacent ground-level position, send one ordinary first-option interaction to the nearby door. Success requires a subsequently decoded client-visible location removal or replacement at the target coordinate; the request alone is not success, and a timeout or rejection without that evidence is `unknown`. Observe the client position and framing throughout, avoid repeated clicks, and log out cleanly. This experiment does not yet prove that the character can walk through the doorway or that it will remain open.

The ordinary client sent one `Open` request. A subsequent zone update reported removal of the target door at the expected coordinate and shape. The player's position did not change, and there were no reported framing or zone-decoding errors. The observation satisfies the defined door-change criterion but does not independently prove the complete doorway state.

## Doorway and ladder experiment defined before running

From the same observed start, request the door's first option once. Only if the client subsequently observes the target door removal, calculate a bounded cardinal path using the static snapshot with that placement removed and request movement to an adjacent ladder tile. Only if the client observes arrival, request the ladder's first `Climb-up` option. Walking succeeds if the observed position reaches the selected adjacent tile. Climbing succeeds only if a subsequent client player update reports a higher level. Otherwise report the appropriate stage as `unknown`, stop on framing or decoding errors, and log out cleanly. A static snapshot with one observed change applied is not a fully reconciled dynamic scene.

The first attempt stopped before any new request because a location change at the door was already observed during initial scene updates; the prototype treated this as uncertain rather than assume the door had reset. The character remained at its starting position. A subsequent read-only session observed removal of the original door and addition of another door location on the adjacent tile, consistent with an open door, but did not independently validate all surrounding state.

Before a second attempt: require that same removal and adjacent addition in the new session, and do not click the already changed door. The previously calculated four-step path to the ladder-adjacent tile does not cross the added wall's observed edge. Send that bounded path only if the start and observed changes match; once arrival is reported, request `Climb-up` once and require an observed level increase for success. Abort on relevant further changes or decoding errors. This is a targeted experiment, not general dynamic collision reconciliation.

The second attempt observed the expected removal and addition. The character followed all four waypoints through the doorway to the ladder-adjacent tile. One first-option ladder interaction was then sent, and a subsequent player update showed the character on level 1 at the same horizontal position. No relevant further door changes or reported framing or decoding errors occurred. Both the doorway traversal and the predeclared climb-up criterion were observed. At this checkpoint climbing down had not yet been tested; the later loop tested it. Automatic interaction planning, general dynamic collision reconstruction, and other doors or ladders remain unverified.

## Retained demonstration

The specific loop driver is retained as `tools/headless-experiment/demos/door-ladder-demo.mjs`. It is tied to this observed location, object IDs, route, and starting positions; it is not a general navigation API. It expects the ordinary character outside the door or at the interior tile immediately beside it. It stops when observations or checkpoints are missing. Set `RUNEHIVE_EXPERIMENT_HOST` to the shared server and provide the disposable account through `RUNEHIVE_EXPERIMENT_ACCOUNT`; do not place credentials in source, shell history, experiment logs, or documentation. The experiment prints position and progress but not credentials. There is a 30-second recording countdown. It requests clean logout when finished or stopped.

## Five-loop demonstration defined before running

For the owner's video, use the same prepared character and nearby targets. Start upstairs; request the client-visible `Climb-down` option, observe level 0, walk through the open doorway to the outside tile, and request the open door's `Close` option. For each of five loops, observe the closed door, request `Open`, observe its removal and open replacement, walk to the ladder, request `Climb-up` and observe level 1, request `Climb-down` and observe level 0, walk outside, request `Close`, and observe the closed replacement. Stop on unconfirmed arrival, unrecognized scene state, framing/decoding errors, or deadlines rather than guessing. The desired final state is outside, on level 0, with a client-observed closed door. This is a fixed, carefully bounded demonstration, not general action planning.

The initial attempt climbed down but stopped when it could not confirm the door state. A retry from the ground floor stopped before moving for the same reason. A revised attempt then reached the outside tile but did not reach the planned adjacent tile; the static client map shows a wall edge between them. No loop completed. Next, from the observed outside tile, send one `Close` request to the observed open door and require a subsequent closed-door replacement for success; stop without assuming the attempt worked.

That request produced no observed door change within the deadline, so its outcome is unknown. Before the next attempt: if the same open door is observed, walk one tile into the doorway, request `Close` once from the tile adjacent to the open door, and require the closed replacement to be observed. Only then walk one tile north to the outside, and confirm arrival. Stop if any prerequisite or observation is missing.

This threshold close and exit succeeded. A subsequent five-loop attempt completed one full loop and stopped during the second after arrival could not be confirmed. The owner reported closing the door during that loop; the timeout alone did not establish the cause. Before recovery: observe the character inside next to the door and the relevant full-zone refresh against the validated static closed-door placement, check for later contradictory updates, request `Open` once, and require its removal and open-door replacement. Then walk into the threshold, request `Close` once, and walk outside only after the closed replacement is observed. Stop on any unconfirmed state.

The recovery observed the door opening, walked through, observed it closing, and reached the outside. The revised retained demonstration then completed all five loops: it observed each door opening, climb up and down, closure, and return outside. During the second loop it requested and observed an additional opening on the way out; the cause of the door state is not established. The final client-observed state was ground level outside, with the door observed closed. The driver requested logout; it did not separately record confirmation of the logout. This is a location-specific scripted recovery and does not establish general autonomous obstacle handling.

## Lessons for the headless client

- **Interaction is part of navigation.** A route may require changing the environment or level, not just walking waypoints. In this example the useful sequence combined door, walking and ladder actions; the script supplied that sequence explicitly.
- **Choose options from current client-visible targets.** The nearby location definitions exposed `Open`, `Close`, `Climb-up` and `Climb-down` in specific option slots. The open and closed door were represented by different locations, and the upstairs ladder had different options from the downstairs ladder. Do not assume one object ID, option slot or action applies to every door or ladder.
- **Static map data is only a baseline.** Zone updates reported a removal and an adjacent addition when this door opened. A scene tracker needs to combine loaded definitions and placements with live changes, and account for full-zone refreshes, build-area and level changes, timing, and lost packets. The loop's special-case flags are not a complete scene reconciler.
- **Arrival is not guaranteed by a request.** The planned outside-adjacent tile was across a wall, and a close request from another position produced no observed result. Neither timeout established why. The successful close was requested from the doorway threshold, followed by an observed door replacement and a separate confirmed step outside.
- **Other players can invalidate a route.** The owner reported closing the door during the interrupted loop. The first driver stopped at an unconfirmed arrival. The revised driver could reopen this known door and retry after receiving the expected updates, but this recovery is hard-coded; it is not proof that arbitrary obstacles can be identified or handled.
- **Observe every transition.** The experiment gated its next step on client-reported location changes or player position/level changes. A successful door update or level change supports the specific observed outcome, not a guarantee about later state or all nearby terrain. A lost or incomplete update must leave the result unknown.

## Follow-up

Implement and test a live location scene that survives zone and level transitions, represents uncertainty explicitly, and updates collision safely. Add general interaction-aware route planning and interruption/replanning only after the client can identify targets and options from current observations. Test other doors and ladders independently, including their interaction reach and resulting state; retain the focused demonstration as a regression/reference scenario rather than treating its fixed coordinates as a production capability.
